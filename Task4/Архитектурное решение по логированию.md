### Системы, из которых требуется сбор логов

На основе анализа C4-диаграммы системы «Александрит» выделены следующие компоненты, из которых необходимо собирать логи:

1. **Shop API (Java Spring Boot)** — бэкенд онлайн-магазина, точка входа клиентских заказов.
2. **CRM API (Java Spring Boot)** — бэкенд CRM, подтверждение заказов и взаимодействие с MES через RabbitMQ.
3. **MES API (C#)** — бэкенд MES, назначение заказов на операторов, расчёт стоимости, B2B API.
4. **RabbitMQ** — очередь сообщений между CRM и MES, критическая точка потери заказов.
5. **Shop DB (PostgreSQL)** — общая БД для Shop API и CRM API, логи медленных запросов.
6. **MES DB (PostgreSQL)** — БД MES, логи медленных запросов.

Фронтенд-приложения (Internet Shop, CRM, MES UI) не включены в периметр серверного логирования — ошибки на фронтенде отслеживаются через метрики API (коды ответов, latency).

| **FATAL** | Полный отказ сервиса, невозможность продолжить работу     | Невозможно подключиться к БД при старте; исчерпание памяти (OOM); критический сбой JVM/.NET runtime                                                                                                   |

## 2. Мотивация

### Почему необходимо логирование

Сейчас разбор инцидентов происходит **со слов клиента**: клиент описывает проблему, поддержка передаёт описание разработчикам, те пытаются воспроизвести ситуацию. Этот процесс:

- Занимает **часы и дни** — пока информация дойдёт до разработчика, контекст утерян.
- **Неточен** — клиент описывает симптомы, а не причину; ключевые детали (время, идентификаторы) часто отсутствуют.
- **Нагружает поддержку** — специалисты поддержки вынуждены вручную собирать информацию, вместо того чтобы сразу видеть логи.

Централизованное логирование позволит **любому члену команды** за минуты найти информацию о конкретном заказе, ошибке или событии, введя `order_id` или `customer_id` в поисковой строке.

### Метрики, на которые повлияет внедрение логирования

**Технические метрики:**

1. **MTTR (Mean Time to Resolve)** — среднее время устранения инцидента. Сейчас разбор одного инцидента занимает от нескольких часов до дней. С логами поддержка и разработчики смогут найти причину за минуты. Ожидаемое улучшение: **сокращение MTTR на 50–70%**.

2. **MTTD (Mean Time to Detect)** — среднее время обнаружения проблемы. Сейчас проблемы обнаруживаются по жалобам клиентов (реактивно). С алертингом на основе логов (всплеск ERROR, отсутствие ожидаемых INFO-записей) команда узнает о проблемах **до клиентов**. Ожидаемое улучшение: **сокращение MTTD с часов до минут**.

3. **Error Rate по компонентам** — процент ошибок в каждом сервисе. Без логов эта метрика вычисляется только по HTTP-кодам ответа (из мониторинга). С логами можно отслеживать и внутренние ошибки, которые не отражаются в HTTP-ответах (например, ошибки записи в RabbitMQ, частичные сбои бизнес-логики).

**Бизнес-метрики:**

4. **Количество обращений в поддержку, требующих эскалации на разработку** — сейчас большинство обращений требуют подключения разработчиков. С логами поддержка сможет самостоятельно находить информацию по `order_id`. Ожидаемое улучшение: **снижение эскалаций на 40–60%**.

5. **Время обработки обращения клиента** — среднее время от получения обращения до ответа клиенту. С доступом к логам поддержка сможет отвечать быстрее: «Ваш заказ №X находится на этапе расчёта стоимости, ожидаемое время — Y минут». Ожидаемое улучшение: **сокращение на 30–50%**.

## 3. Приоритизация: логирование и трейсинг в первую очередь

Единовременно внедрить логирование и трейсинг для всех систем невозможно. Приоритизация основана на критичности компонента для бизнеса и частоте возникающих проблем.

### Первый приоритет (этап 1)

| Система      | Логирование | Трейсинг | Обоснование                                                                                                                                                                                                                         |
| ------------ | ----------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **CRM API**  | Да          | Да       | Ключевая точка подтверждения заказов (MANUFACTURING_APPROVED). Именно здесь заказ передаётся в MES через RabbitMQ — основное место потерь.                                                                                          |
| **MES API**  | Да          | Да       | Расчёт стоимости (2–30 минут) — главная «чёрная дыра» для заказов. B2B-заказы проходят через MES API, и их потеря ведёт к разрыву контрактов.                                                                                       |
| **RabbitMQ** | Да          | —        | Единая точка отказа для обмена между CRM и MES. Логи покажут, какие сообщения теряются, зависают, попадают в DLQ. Трейсинг RabbitMQ обеспечивается через context propagation в заголовках сообщений (на стороне CRM API и MES API). |

**Почему:** Эти три компонента составляют критический путь заказа от подтверждения до производства. Именно здесь происходят потери, которые приводят к оттоку клиентов и разрыву B2B-контрактов.



## 4. Предлагаемое решение

### Технологический стек

| Компонент                 | Технология        | Обоснование                                                                                                                                                                |
| ------------------------- | ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сбор и доставка логов     | **Filebeat**      | Легковесный агент, устанавливается на каждый EC2-инстанс. Собирает логи из файлов приложений и пересылает в Logstash. Минимальное потребление ресурсов.                    |
| Обработка и трансформация | **Logstash**      | Конвейер обработки: парсинг JSON-логов, обогащение (добавление полей service_name, environment), фильтрация, маршрутизация в нужный индекс Elasticsearch.                  |
| Хранение и поиск          | **Elasticsearch** | Документоориентированная БД с полнотекстовым поиском. Быстрый поиск по `order_id`, `customer_id`, `trace_id`. Шардирование и ILM для управления жизненным циклом индексов. |
| Визуализация и анализ     | **Kibana**        | Дашборды для поддержки и разработчиков. Поиск по логам, визуализация ошибок, создание отчётов.                                                                             |

### Компоненты, которые нужно внедрить или доработать

**Новые компоненты (выделены красным на схеме):**

1. **Filebeat** — устанавливается на каждый EC2-инстанс (Shop API, CRM API, MES API). Читает лог-файлы приложений и отправляет в Logstash.

2. **Logstash** — развёртывается как отдельный сервис. Принимает логи от Filebeat, парсит, обогащает (добавляет `service_name`, `environment`, `trace_id`), маршрутизирует в соответствующий индекс Elasticsearch.

3. **Elasticsearch** — хранилище логов. Если кластер Elasticsearch уже развёрнут для трейсинга (Task3), используется тот же кластер с отдельными индексами для логов. Рекомендуется Managed Elasticsearch в Yandex Cloud.

4. **Kibana** — веб-интерфейс для поиска и визуализации логов. Если уже развёрнута для трейсинга, дополнительная установка не требуется — создаются новые index patterns и дашборды.

**Доработка существующих компонентов:**

5. **Shop API (Java Spring Boot):**
   - Настроить Logback для вывода логов в формате JSON в файл.
   - Добавить структурированное логирование бизнес-событий (создание заказа, загрузка файла, смена статуса).
   - Добавить `trace_id` и `span_id` из OpenTelemetry в MDC (Mapped Diagnostic Context) для корреляции с трейсами.

6. **CRM API (Java Spring Boot):**
   - Аналогично Shop API: Logback JSON + бизнес-события + MDC с trace_id.
   - Логирование всех операций отправки/получения сообщений RabbitMQ с `correlation_id`.

7. **MES API (C#):**
   - Настроить Serilog для вывода логов в формате JSON в файл.
   - Добавить структурированное логирование бизнес-событий.
   - Добавить `trace_id` из OpenTelemetry через `Activity.Current?.TraceId`.

8. **RabbitMQ:**
   - Включить встроенное логирование RabbitMQ в файл (JSON-формат).
   - Установить Filebeat на инстанс RabbitMQ для отправки логов.

9. **PostgreSQL (Shop DB, MES DB):**
   - Включить `log_min_duration_statement = 500` для логирования медленных запросов.
   - Установить Filebeat на инстансы БД для отправки логов slow queries.

## 5. Политика безопасности

### Работа с чувствительными данными

1. **Маскирование персональных данных.** В логах запрещено хранить в открытом виде: ФИО клиентов, email, телефоны, платёжные данные. Если эти данные необходимы для отладки, они маскируются на уровне Logstash

2. **Запрет логирования секретов.** Пароли, токены, API-ключи, данные сессий не должны попадать в логи. Это контролируется через code review и статический анализ.

3. **Идентификаторы вместо данных.** В логах используются `customer_id`, `order_id`, `operator_id` вместо персональных данных. При необходимости данные можно получить из БД по идентификатору.

## 6. Анализ логов: алертинг и обнаружение аномалий

### Алертинг

Необходимо настроить алерты в Kibana (или через Elastalert) на следующие ситуации:

| Алерт                    | Условие                                                       | Канал уведомления                   | Критичность |
| ------------------------ | ------------------------------------------------------------- | ----------------------------------- | ----------- |
| Всплеск ошибок           | Количество ERROR-записей >10 за 5 минут для любого сервиса    | Telegram + email                    | Высокая     |
| FATAL-событие            | Любая запись уровня FATAL                                     | Telegram + email + звонок дежурному | Критическая |
| Сообщения в DLQ          | Появление записей о попадании сообщений в Dead Letter Queue   | Telegram                            | Высокая     |
| Отсутствие логов         | Нет ни одной записи от сервиса за 5 минут (сервис мог упасть) | Telegram                            | Критическая |
| Медленные запросы БД     | >5 записей slow query за 10 минут                             | Email                               | Средняя     |
| Неудачные аутентификации | >20 неудачных попыток входа за 5 минут (brute-force)          | Telegram + email                    | Высокая     |

### Обнаружение аномалий

Да, необходимо настроить обнаружение аномалий. Примеры:

1. **Аномальный рост количества заказов.** Обычно создаётся ~4 заказа в минуту, а внезапно стало 10 000 — возможна DDoS-атака конкурентов или бот-активность. Реализация: Kibana Anomaly Detection (ML) или Elastalert с spike-правилом.

2. **Аномальный рост ошибок RabbitMQ.** Если количество rejected/DLQ сообщений резко выросло — возможен сбой потребителя или изменение формата сообщений.

3. **Аномальное время расчёта стоимости в MES.** Если среднее время расчёта выросло с 5 минут до 25 минут — возможна проблема с ресурсами или данными.

4. **Аномальное количество запросов от одного B2B-пользователя.** Выявление нарушителей rate-limit или скомпрометированных API-ключей.

Для обнаружения аномалий рекомендуется использовать **Kibana Machine Learning** (доступно в Elastic License) или, если используется OpenSearch, — **OpenSearch Anomaly Detection plugin**.
