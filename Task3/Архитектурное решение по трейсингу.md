## 1. Анализ системы: проблемные зоны, требующие покрытия трейсингом

### Схема с выделенными проблемными зонами

[Схема проблемных зон (bad_regions.drawio)](bad_regions.drawio)

### Идентифицированные проблемные точки

На основе анализа C4-диаграммы и жизненного цикла заказа выделены пять зон, где заказ может «сломаться» или зависнуть:

**Зона 1. Shop API**
- Ошибка при сохранении заказа в Shop DB (общая БД с CRM API — конкуренция за ресурсы приводит к блокировкам и таймаутам).
- Ошибка при загрузке 3D-файла в S3-хранилище.
- Заказ создан, но информация о нём не дошла до CRM/MES.

**Зона 2. CRM API**
- Сообщение о новом заказе может быть потеряно при публикации в RabbitMQ.
- CRM API может не обработать входящее сообщение от MES о рассчитанной стоимости (PRICE_CALCULATED).
- Подтверждение заказа (MANUFACTURING_APPROVED) может не дойти обратно до MES.

**Зона 3. MES API**
- Расчёт стоимости занимает 2–30 минут — процесс может завершиться по таймауту, результат потеряется.
- B2B-запросы через API создают дополнительную нагрузку, конкурируя с внутренними заказами.
- Изменение статусов (MANUFACTURING_STARTED → SHIPPED) может не дойти до CRM через RabbitMQ.

**Зона 4. RabbitMQ (транспорт между CRM и MES)**
- Единая точка отказа (один инстанс, нет кластеризации).
- Отсутствие Dead Letter Queue — отклонённые сообщения теряются безвозвратно.
- Нет механизма retry при временных сбоях.
- Сообщения могут зависнуть в состоянии unacked.

**Зона 5. Shop DB (общая база данных)**
- Shop API и CRM API конкурируют за ресурсы одной базы PostgreSQL.
- Медленные запросы от одного сервиса блокируют другой.
- При высокой нагрузке возможны deadlock'и, приводящие к потере транзакций.

### Данные, которые должны попадать в трейсинг

| Данные           | Описание                                                       |
| ---------------- | -------------------------------------------------------------- |
| `trace_id`       | Уникальный идентификатор всей цепочки вызовов по заказу        |
| `span_id`        | Идентификатор каждого отдельного шага обработки                |
| `parent_span_id` | Идентификатор родительского span для построения дерева вызовов |
| `order_id`       | Идентификатор заказа — ключевой бизнес-атрибут для поиска      |
| `customer_id`    | Идентификатор клиента                                          |
| `order_status`   | Текущий и предыдущий статус заказа                             |
| `service_name`   | Имя сервиса, обрабатывающего запрос                            |
| `operation_name` | Название операции                                              |
| `duration_ms`    | Длительность операции в миллисекундах                          |
| `timestamp`      | Время начала и окончания каждого span                          |

## 2. Мотивация

### Почему необходим трейсинг

Компания «Александрит» сталкивается с критической бизнес-проблемой: заказы теряются или зависают на неизвестных этапах обработки внутри распределённой системы из трёх приложений (Онлайн-магазин, CRM, MES). Заказ проходит через множество компонентов и асинхронных взаимодействий через RabbitMQ, и при текущем уровне наблюдаемости невозможно:

1. **Определить, на каком этапе находится заказ.** Клиент жалуется, что заказ не выполнен, но команда не может сказать — заказ застрял в RabbitMQ, не дошёл до MES или ожидает подтверждения в CRM.

2. **Найти причину потери заказа.** Сообщение могло потеряться в RabbitMQ, Shop API мог не записать заказ в общую Shop DB из-за конкуренции с CRM, MES мог отвалиться по таймауту при расчёте стоимости.

3. **Оценить время прохождения заказа по этапам.** Нет данных о том, сколько времени заказ проводит на каждом этапе, что мешает выявить узкие места.

4. **Воспроизвести проблему.** Без контекста вызовов разработчик может лишь угадывать причину сбоя. Создавать подробные логи на все места — дорого и неэффективно.

Трейсинг решает эти проблемы, предоставляя **сквозную видимость пути заказа** от момента создания до закрытия, с возможностью увидеть каждый шаг, его длительность и результат.

### Метрики, на которые повлияет внедрение трейсинга

**Технические метрики:**

1. **MTTR (Mean Time to Resolve)** — среднее время устранения инцидента. Сейчас разбор проблемы «со слов клиента» занимает часы или дни. С трейсингом инженер сможет за минуты найти конкретный span, где произошёл сбой. Ожидаемое улучшение: сокращение MTTR на 60–80%.

2. **Order Success Rate** — процент заказов, прошедших все этапы без ошибок. Трейсинг позволит обнаруживать «тихие» сбои, когда заказ формально не упал с ошибкой, но завис между сервисами. Целевое значение: >99%.

3. **Latency по этапам обработки заказа (P95/P99)** — трейсинг покажет, какой этап является узким местом (например, расчёт стоимости в MES или подтверждение в CRM). Позволит таргетированно оптимизировать самые медленные участки.

**Бизнес-метрики:**

4. **Количество потерянных заказов в месяц** — прямое влияние на выручку. Трейсинг позволит выявлять потери в реальном времени и реагировать проактивно. Целевое значение: снижение на 90%+ в первые 3 месяца.

5. **NPS / удовлетворённость клиентов (B2C и B2B)** — быстрое решение проблем с заказами и проактивное информирование клиентов повысит лояльность. B2B-партнёры перестанут разрывать контракты из-за «потерянных» заказов.

## 3. Предлагаемое решение

### Технологический стек

| Компонент                        | Технология                   | Обоснование                                                                                                                                                      |
| -------------------------------- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Стандарт инструментирования      | **OpenTelemetry (OTel)**     | Отраслевой стандарт; поддержка Java (Spring Boot) и C# (.NET); vendor-neutral; поддержка context propagation через HTTP-заголовки и заголовки сообщений RabbitMQ |
| Коллектор телеметрии             | **OpenTelemetry Collector**  | Центральная точка приёма, обработки и маршрутизации телеметрии; фильтрация, семплирование и экспорт данных; развязка сервисов от бэкенда трейсинга               |
| Бэкенд трейсинга                 | **Jaeger**                   | Визуализация трассировок; поиск по trace_id, service, duration; нативная поддержка OTel; веб-интерфейс Jaeger UI для команды поддержки                           |
| Хранилище трейсов                | **Elasticsearch**            | Масштабируемое хранение трейсов с полнотекстовым поиском; поддерживается Jaeger; managed-сервис в Yandex Cloud                                                   |
| SDK для Java (Shop API, CRM API) | **OpenTelemetry Java Agent** | Авто-инструментация — минимальные изменения в коде; перехват Spring Boot, JDBC, RabbitMQ                                                                         |
| SDK для C# (MES API)             | **OpenTelemetry .NET SDK**   | Авто-инструментация ASP.NET Core, HttpClient, RabbitMQ client, Npgsql                                                                                            |

### Компоненты, которые нужно внедрить или доработать

**Новые компоненты (выделены красным на схеме):**

1. **OpenTelemetry Collector** — развёртывается как отдельный сервис (EC2-инстанс). Принимает телеметрию от всех API-сервисов по протоколу OTLP (gRPC). Обрабатывает, фильтрует, семплирует и экспортирует в Jaeger.

2. **Jaeger (Collector + Query + UI)** — развёртывается как отдельный сервис. Включает Jaeger Collector для приёма трейсов, Jaeger Query для поиска и Jaeger UI для визуализации.

3. **Elasticsearch** — хранилище для трассировок Jaeger. Рекомендуется Managed Elasticsearch в Yandex Cloud для упрощения операционной поддержки.

**Доработка существующих компонентов:**

4. **Shop API (Java Spring Boot):**
   - Подключить OpenTelemetry Java Agent
   - Автоматическая инструментация: Spring Boot MVC, RestTemplate/WebClient, JDBC (PostgreSQL), S3 Client.

5. **CRM API (Java Spring Boot):**
   - Подключить OpenTelemetry Java Agent.
   - Автоматическая инструментация: Spring Boot MVC, JDBC, spring-rabbit (RabbitMQ).

6. **MES API (C# .NET):**
   - Подключить OpenTelemetry .NET SDK с авто-инструментацией.
   - Инструментация: ASP.NET Core, HttpClient, RabbitMQ .NET Client, Npgsql.
   - Context propagation через RabbitMQ message headers (W3C Trace Context).

## 4. Компромиссы

### Где трейсинг не принесёт пользы или обойдётся слишком дорого

1. **Фронтенд-приложения (Internet Shop, CRM, MES UI).** Внедрение трейсинга на стороне браузера (через OTel JS SDK) технически возможно, но создаёт дополнительный сетевой трафик от каждого пользователя, а персональные данные могут попасть в трассировки. Для основной задачи — отслеживания заказов — достаточно трейсинга на уровне API. **Решение:** не инструментировать фронтенд; трейсинг начинается с момента поступления запроса в API.

2. **Внутренние процессы S3-хранилища.** Загрузка/чтение 3D-файлов инструментируется на уровне SDK (S3 Client), но трейсинг не может проникнуть внутрь managed-сервиса S3. Мы увидим только задержку и код ответа, но не причину внутренней проблемы. Это допустимо, так как S3 имеет собственный SLA.

3. **Внутренние процессы PostgreSQL.** Трейсинг покажет SQL-запросы и их длительность через JDBC/Npgsql-инструментацию, но не отследит внутренние процессы БД (deadlocks, vacuum, replication lag). Для этого существуют инструменты мониторинга на уровне БД (pg_stat_statements, pg_locks), реализуемые в рамках задачи по мониторингу.

4. **RabbitMQ как «чёрный ящик».** Мы можем передавать trace context через заголовки сообщений и инструментировать producers/consumers. Однако время нахождения сообщения в очереди (queue dwell time) не является стандартным span'ом. Для его отслеживания необходима доработка: фиксация timestamp отправки в message header и вычисление разницы при получении. Это не из коробки.

5. **Внешний B2B API.** Мы не контролируем, как B2B-партнёры отправляют запросы. Если партнёр не передаёт заголовки W3C Trace Context, создаётся новый trace. Полной сквозной трассировки «от партнёра до готового изделия» не будет без договорённости о передаче trace context.

## 5. Безопасность

### Меры для предотвращения несанкционированного доступа

**Внутренний доступ к системе трейсинга:**

1. **Аутентификация через корпоративную учётную запись.** Доступ к Jaeger UI предоставляется только сотрудникам компании с актуальной учётной записью. Реализация — через reverse proxy (nginx) с интеграцией с корпоративным IdP (OAuth2/OIDC). Зайти в систему смогут только сотрудники компании с актуальной учетной записью и соответствующей ролью.

2. **Ролевая модель доступа (RBAC):**
   - Роль **«Поддержка»** — просмотр трассировок, поиск по order_id / customer_id. Доступна продавцам и продакт-менеджеру.
   - Роль **«Разработчик»** — полный доступ к трассировкам, включая SQL-запросы и технические детали span'ов.
   - Роль **«Администратор»** — управление конфигурацией OTel Collector, семплированием, retention-политиками Elasticsearch. Доступна DevOps-инженеру и тимлиду.

3. **Сетевая изоляция.** Jaeger UI, OTel Collector и Elasticsearch развёрнуты в приватной подсети VPC Yandex Cloud. Доступ к Jaeger UI — только через VPN или корпоративную сеть. OTel Collector принимает данные только от известных сервисов (whitelist по security group).

4. **Шифрование данных:**
   - TLS для передачи данных от сервисов к OTel Collector (OTLP/gRPC с TLS).
   - TLS для передачи от OTel Collector к Jaeger и Elasticsearch.
   - Encryption at rest для Elasticsearch (managed-сервис Yandex Cloud поддерживает из коробки).

5. **Аудит доступа.** Все обращения к Jaeger UI логируются: кто, когда, какие трассировки просматривал. Необходимо для compliance и расследования инцидентов доступа к данным.

6. **Jaeger UI не доступен из интернета.** Нет необходимости предоставлять доступ к трейсингу внешним пользователям (B2B-партнёрам). B2B-партнёры получают информацию о статусе заказа через API, а не через внутреннюю систему трейсинга.
