# Выбор и настройка мониторинга в системе

## 1. Мотивация

### Почему необходим мониторинг

Компания «Александрит» столкнулась с рядом серьёзных проблем, которые напрямую влияют на бизнес:

1. **Потеря заказов.** Клиенты (B2C и B2B через API) сообщают, что не получают свои заказы. Компания уже потеряла несколько крупных контрактов. Без мониторинга невозможно определить, на каком этапе и почему заказы «теряются» — в RabbitMQ, при обработке в MES или CRM.

2. **Просроченные заказы.** Клиенты жалуются на сроки выполнения в несколько месяцев вместо обещанных трёх недель. При этом производственные мощности позволяют справиться с нагрузкой. Это указывает на проблему в IT-системах, а не в производстве. Мониторинг позволит выявить «узкое горлышко».

3. **Деградация производительности MES.** Операторы жалуются на медленную загрузку первой страницы MES (дашборд заказов). Пагинация и фильтры не помогли. Без метрик времени отклика и нагрузки на БД невозможно диагностировать причину.

4. **Линейный рост нагрузки.** Каждый месяц компания получает на 100 заказов больше. Без мониторинга невозможно прогнозировать, когда система достигнет предела, и заранее масштабировать инфраструктуру.

5. **Отсутствие полной картины после открытия API.** Яндекс Метрика покрывает только веб-интерфейс онлайн-магазина. Заказы через API (B2B) полностью вне зоны видимости.

### Что даст мониторинг компании

- **Проактивное обнаружение проблем** — команда узнает о сбоях раньше клиентов.
- **Сокращение времени диагностики** — вместо разбора со слов клиента, команда сможет посмотреть метрики и быстро локализовать проблему.
- **Обоснованное планирование мощностей** — данные о тренде нагрузки позволят заранее масштабировать инфраструктуру.
- **Снижение оттока клиентов** — быстрое реагирование на проблемы повысит удовлетворённость и сохранит контракты.
- **Данные для приоритизации** — метрики покажут, какие компоненты системы требуют оптимизации в первую очередь.

## 2. Выбор подхода к мониторингу

Для разных частей системы «Александрит» целесообразно использовать разные подходы к мониторингу, поскольку компоненты имеют разную природу.

### RED — для API-сервисов (Shop API, CRM API, MES API)

**Обоснование:** Все три API являются request-driven сервисами. Метод RED (Rate, Errors, Duration) разработан именно для таких сервисов и позволяет отслеживать показатели, которые напрямую влияют на пользовательский опыт. Это наиболее релевантный подход для выявления проблем с потерей заказов и медленной работой системы.

### USE — для инфраструктурных ресурсов (EC2-инстансы, базы данных, S3)

**Обоснование:** Метод USE (Utilization, Saturation, Errors) предназначен для мониторинга ресурсов, производительность которых снижается при интенсивном использовании. Учитывая линейный рост нагрузки (+100 заказов/месяц) и то, что каждое приложение работает на единственном EC2-инстансе с одним инстансом БД, критически важно отслеживать утилизацию и насыщенность, чтобы предотвратить исчерпание ресурсов.

### Четыре золотых сигнала — для RabbitMQ

**Обоснование:** RabbitMQ является центральным элементом интеграции между CRM и MES. Метод золотых сигналов (Latency, Traffic, Errors, Saturation) даёт наиболее полную картину для очереди сообщений: важно отслеживать как скорость доставки (latency), так и объём трафика, ошибки и насыщенность очереди. Именно здесь, вероятнее всего, теряются заказы.

## 3. Метрики для отслеживания

### 3.1. RabbitMQ (Четыре золотых сигнала)

#### Number of dead-letter-exchange letters in RabbitMQ
- Сообщения в DLX — это заказы, которые не были обработаны. Рост DLX напрямую коррелирует с потерей заказов. Это критическая метрика для решения проблемы потерянных заказов.
- **Ярлыки:** `queue` (имя очереди-источника), `reason` (причина попадания в DLX: expired, rejected, max-length)

#### Number of messages in flight in RabbitMQ
- Показывает количество сообщений, которые были отправлены потребителю, но ещё не подтверждены (unacked). Рост этого показателя указывает на то, что потребитель не успевает обрабатывать сообщения, что может приводить к зависанию заказов.
- **Ярлыки:** `queue` (имя очереди)

### 3.2. Shop API (RED)

#### Number of requests (RPS) for shop API
- Базовая метрика пропускной способности. Позволяет отслеживать пиковые нагрузки, планировать мощности и обнаруживать аномалии (например, DDoS или всплеск трафика).
- **Ярлыки:** `method` (GET/POST/PUT/DELETE), `endpoint` (например, /orders, /products, /upload), `status_code` (2xx/4xx/5xx).

#### Number of requests (RPS) per user for shop API
- Позволяет выявить пользователей с аномально высокой активностью (потенциальные боты или DDoS), а также понять паттерн использования.
- **Ярлыки:** `user_id`, `endpoint`.

#### Response time (latency) for shop API
- Ключевая метрика пользовательского опыта. Позволяет отслеживать деградацию времени отклика, которая приводит к снижению конверсии и оттоку клиентов.
- **Ярлыки:** `method`, `endpoint`, `percentile` (p50, p95, p99).

#### Number of HTTP 500 for shop API
- Серверные ошибки означают, что пользователи не могут выполнить целевые действия (оформить заказ, загрузить файл). Рост ошибок 500 может быть причиной потери заказов.
- **Ярлыки:** `endpoint`, `error_type` (классификация ошибки).

#### Number of HTTP 200 for shop API
- В сочетании с общим RPS и количеством ошибок позволяет вычислить success rate — долю успешных запросов.
- **Ярлыки:** `endpoint`.

#### Kb transferred (received) for shop API
- Пользователи загружают 3D-модели, которые могут быть большими файлами. Мониторинг входящего трафика позволяет отслеживать нагрузку на сеть и выявлять аномальные загрузки.
- **Ярлыки:** `endpoint`.

#### Kb provided (sent) for shop API
- Отслеживание исходящего трафика помогает выявить проблемы с передачей данных клиентам (каталоги товаров, изображения).
- **Ярлыки:** `endpoint`.


### 3.3. CRM API (RED)

#### Number of requests (RPS)
- CRM — внутренняя система, но рост нагрузки на неё пропорционален росту заказов. Мониторинг RPS позволяет отслеживать, справляется ли CRM с потоком.
- **Ярлыки:** `method`, `endpoint`, `status_code`.

#### Response time (latency)
- Задержки в CRM API замедляют работу продавцов, что увеличивает время подтверждения заказов (переход в статус MANUFACTURING_APPROVED) и, следовательно, общее время выполнения заказа.
- **Ярлыки:** `method`, `endpoint`, `percentile` (p50, p95, p99).

#### Number of HTTP 500
- Ошибки в CRM API могут приводить к тому, что заказы не переходят в статус MANUFACTURING_APPROVED, зависая в очереди.
- **Ярлыки:** `endpoint`, `error_type`.

#### Number of HTTP 200
- Позволяет вычислить success rate для CRM API.
- **Ярлыки:** `endpoint`.

#### Number of requests (RPS) per user
- Позволяет оценить нагрузку на CRM в разрезе продавцов, выявить аномалии.
- **Ярлыки:** `user_id`, `endpoint`.

### 3.4. MES API (RED)

#### Number of requests (RPS)
- **Зачем:** MES API принимает запросы от операторов (через UI), от API-пользователей (B2B) и от CRM (через RabbitMQ). С момента открытия API нагрузка значительно возросла. Мониторинг RPS критически важен для понимания текущей нагрузки.
- **Ярлыки:** `method`, `endpoint`, `status_code`, `source` (ui / api / rabbitmq).

#### Number of requests (RPS) per user
- **Зачем:** Позволяет выявить API-пользователей, создающих чрезмерную нагрузку. Особенно важно после открытия публичного API.
- **Ярлыки:** `user_id`, `endpoint`, `user_type` (operator / api_user).

#### Response time (latency)
- **Зачем:** Операторы жалуются на медленную загрузку первой страницы MES. Мониторинг latency по эндпоинтам позволит точно локализовать проблему (дашборд заказов или другие операции).
- **Ярлыки:** `method`, `endpoint`, `percentile` (p50, p95, p99).

#### Number of HTTP 500
- **Зачем:** Ошибки в MES API могут приводить к потере заказов от B2B-партнёров и к невозможности операторов работать с заказами.
- **Ярлыки:** `endpoint`, `error_type`.

#### Number of HTTP 200
- **Зачем:** Вычисление success rate. Особенно важно для API-эндпоинтов, доступных B2B-партнёрам.
- **Ярлыки:** `endpoint`.

#### Number of simultaneous sessions
- **Зачем:** Операторы конкурируют за заказы (кто взял заказ — тот получает оплату), что стимулирует одновременную работу. Мониторинг числа сессий позволяет понять, сколько пользователей работает одновременно и коррелирует ли это с деградацией производительности.
- **Ярлыки:** `user_type` (operator / api_user).

#### Kb transferred (received)
- **Зачем:** MES принимает 3D-модели через API для расчёта стоимости. Объём входящих данных влияет на нагрузку.
- **Ярлыки:** `endpoint`.

#### Kb provided (sent)
- **Зачем:** Отслеживание исходящего трафика, включая ответы API-пользователям (результаты расчёта стоимости).
- **Ярлыки:** `endpoint`.

### 3.5. Инфраструктура — EC2-инстансы (USE)

#### CPU %
- **Зачем:** Утилизация CPU. При работе на единственном инстансе критически важно отслеживать приближение к пределу.
- **Ярлыки:** `instance_id`, `service`.

#### Memory Utilisation
- **Зачем:** приложения склонны к утечкам памяти и высокому потреблению heap. Мониторинг утилизации памяти предотвращает OOM-ситуации.
- **Ярлыки:** `instance_id`, `service`.

### 3.6. Инфраструктура — базы данных (USE)

#### Memory Utilisation for DB instance
- БД использует оперативную память для кеширования данных (shared_buffers). Нехватка памяти приводит к интенсивному дисковому I/O и деградации производительности запросов.
- **Ярлыки:** `instance_id`, `db` (shop-db).

#### Number of connections for MES DB instance
- Аналогично Shop DB, плюс MES DB обслуживает как операторов через UI, так и API-пользователей.
- **Ярлыки:** `instance_id`, `db` (mes-db), `state` (active / idle / idle_in_transaction).

#### Size of Shop DB instance
- Мониторинг объёма БД позволяет прогнозировать рост и заранее планировать расширение хранилища. Линейный рост заказов приводит к линейному росту данных.
- **Ярлыки:** `instance_id`, `db`.

### 3.7. Инфраструктура — S3 (USE)

#### Size of S3 storage
- **Зачем:** 3D-файлы могут быть значительного размера. С ростом заказов объём S3 растёт линейно. Мониторинг позволяет контролировать затраты на хранение и планировать бюджет.
- **Ярлыки:** `bucket`.

## 4. План действий

### Этап 1. Подготовка инфраструктуры мониторинга

1. **Развернуть Prometheus** на отдельном EC2-инстансе в Yandex Cloud для сбора метрик по модели pull. Prometheus — де-факто стандарт для сбора метрик в облачной среде, поддерживает интеграцию со SpringBoot (Micrometer) и C# (prometheus-net).

2. **Развернуть Grafana** на том же или отдельном инстансе для визуализации метрик. Grafana поддерживает Prometheus как data source из коробки и позволяет создавать дашборды, алерты и отчёты.

3. **Настроить Alertmanager** (компонент Prometheus) для отправки уведомлений о критических ситуациях. Настроить каналы уведомлений: корпоративный мессенджер (Telegram/Slack), email.

### Этап 2. Инструментирование приложений

4. **Подключить Micrometer + Prometheus exporter к Shop API и CRM API** (Java SpringBoot). SpringBoot Actuator + Micrometer позволяют экспортировать метрики RED (RPS, latency, errors) с минимальными изменениями кода.

5. **Подключить prometheus-net к MES API** (C#). Добавить middleware для сбора метрик HTTP-запросов (RPS, latency, status codes).

6. **Добавить кастомные бизнес-метрики** в код приложений: количество заказов по статусам, время нахождения в каждом статусе, количество заказов, ожидающих расчёта.

7. **Настроить RabbitMQ Prometheus plugin** для экспорта метрик очереди (queue depth, DLX count, messages in flight, publish/consume rate).

### Этап 3. Мониторинг инфраструктуры

8. **Установить node_exporter** на все EC2-инстансы для сбора метрик USE (CPU, memory, disk, network).

9. **Настроить postgres_exporter** для обоих инстансов PostgreSQL (Shop DB, MES DB) — сбор метрик connections, database size, query performance.

10. **Настроить мониторинг S3** через Yandex Cloud Monitoring API или CloudWatch-compatible exporter.

### Этап 4. Создание дашбордов и алертов

11. **Создать дашборд «Обзор системы»** в Grafana — общая карта здоровья всех компонентов (Shop API, CRM API, MES API, RabbitMQ, БД).

12. **Создать дашборд «Заказы»** — бизнес-метрики: распределение по статусам, среднее время в статусе, количество «застрявших» заказов.

13. **Создать дашборд «MES Performance»** — фокус на проблеме медленного дашборда MES: latency по эндпоинтам, нагрузка на MES DB, число сессий.

14. **Создать дашборд «RabbitMQ»** — глубина очереди, DLX, publish/consume rate, messages in flight.

15. **Настроить алерты** для критических ситуаций (описаны в разделе 5).
