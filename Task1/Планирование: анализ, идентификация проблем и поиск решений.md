# Планирование: анализ, идентификация проблем и поиск решений

## 1. Описание текущей архитектуры

Система «Александрит» состоит из трёх приложений:

- **Онлайн-магазин**: фронтенд (Vue, TypeScript, ThreeJS) + бэкенд Shop API (Java Spring Boot) + Shop DB (PostgreSQL).
- **CRM**: фронтенд (Vue, TypeScript) + бэкенд CRM API (Java Spring Boot) + **общая с магазином** Shop DB (PostgreSQL).
- **MES**: фронтенд (React, TypeScript) + бэкенд MES API (C#) + MES DB (PostgreSQL).

Интеграции:
- CRM API и MES API обмениваются сообщениями через RabbitMQ (двунаправленная связь).
- Shop API и MES API обращаются к S3-хранилищу 3D-файлов.
- API-пользователи (B2B) обращаются напрямую к MES API для расчёта стоимости.
- Каждое приложение и каждая база данных работают на одном инстансе EC2 (Yandex Cloud).

## 2. Идентифицированные проблемы

| №   | Проблема                                                                          | Описание                                                                                                                                                                                                                     | Влияние на бизнес                                                                                                             |
| --- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| P1  | **Общая база данных Shop DB для Shop API и CRM API**                              | Два независимых сервиса (онлайн-магазин и CRM) работают с одной базой PostgreSQL на чтение и запись. При росте нагрузки возникают блокировки, конкуренция за ресурсы и каскадные деградации производительности.              | Замедление работы магазина и CRM; потенциальная потеря заказов при пиковых нагрузках.                                         |
| P2  | **Единственный инстанс каждого компонента (нет горизонтального масштабирования)** | Все приложения и базы данных имеют по одному инстансу. Нет балансировщика нагрузки, нет реплик чтения для БД.                                                                                                                | Любой компонент является единой точкой отказа (SPOF). При отказе одного инстанса — полный простой соответствующей подсистемы. |
| P3  | **Потеря заказов в RabbitMQ**                                                     | Сообщения о заказах теряются между CRM и MES. Вероятные причины: отсутствие подтверждений (ack), dead-letter-очередей, механизма повторной отправки и идемпотентной обработки.                                               | Клиенты не получают заказы; B2B-партнёры уходят; прямые финансовые потери и репутационный ущерб.                              |
| P4  | **Медленная загрузка дашборда MES**                                               | Первая страница MES (список заказов по статусам) загружается слишком долго. Пагинация и фильтры не решили проблему — вероятно, тяжёлые запросы к MES DB без индексов или с неоптимальными запросами, отсутствие кеширования. | Операторы не могут оперативно брать заказы; снижается пропускная способность производства.                                    |
| P5  | **Отсутствие API Gateway и rate-limiting для внешнего API**                       | B2B-пользователи обращаются напрямую к MES API без посредника. Нет контроля нагрузки, нет throttling, нет квот.                                                                                                              | После открытия API систему «завалило» заказами; MES API перегружается, что влияет и на внутренних операторов.                 |
| P6  | **Отсутствие мониторинга и observability**                                        | Нет централизованного логирования, метрик и трейсинга. Проблемы обнаруживаются по жалобам клиентов.                                                                                                                          | Долгое время реакции на инциденты; невозможность проактивного выявления деградаций.                                           |
| P7  | **Длительный расчёт стоимости (2–30 минут) без обратной связи**                   | MES рассчитывает стоимость синхронно или без уведомления о прогрессе. Клиент не знает статус расчёта.                                                                                                                        | Клиенты думают, что заказ «потерялся»; рост обращений в поддержку.                                                            |
| P8  | **Ручное тестирование как единственный QA-процесс**                               | Один QA-инженер вручную прогоняет E2E-сценарии. Баги блокируют релиз; задержки растут.                                                                                                                                       | Увеличивающиеся задержки релизов; медленное исправление проблем; технический долг накапливается.                              |
| P9  | **Отсутствие read-реплик БД**                                                     | Каждая база данных имеет один инстанс, работающий и на запись, и на чтение.                                                                                                                                                  | Тяжёлые запросы на чтение (дашборд MES, списки заказов) конкурируют с записью, снижая общую производительность.               |
| P10 | **RabbitMQ — единая точка отказа**                                                | Один инстанс RabbitMQ без кластеризации.                                                                                                                                                                                     | При сбое RabbitMQ прекращается обмен между CRM и MES; заказы не проходят по pipeline.                                         |

## 4. Приоритизация инициатив и ход рассуждений

### Принципы приоритизации

1. **Сначала видимость** — без мониторинга мы не знаем, что именно ломается и где. Любые изменения без observability — это работа вслепую.
2. **Затем остановка потерь** — потеря заказов — это прямой финансовый и репутационный ущерб. Это та проблема, из-за которой уходят B2B-клиенты.
3. **Затем защита и стабильность** — API Gateway для контроля внешней нагрузки, чтобы B2B-трафик не «ронял» внутренние системы.
# 5. Топ-3 инициативы на ближайшие полгода

### 1. I1 — Внедрение мониторинга и observability

**Почему:** Это фундамент для любых дальнейших улучшений. Сейчас компания узнаёт о проблемах от клиентов — это реактивный подход с максимальным временем обнаружения. Без мониторинга невозможно:
- Понять, где именно теряются заказы.
- Измерить реальную производительность компонентов.
- Оценить эффект от последующих улучшений.

**Состав работ:**
- Внедрение сбора метрик (Prometheus/Grafana или аналог).
- Централизованное логирование (ELK/OpenSearch).
- Распределённый трейсинг (Jaeger/OpenTelemetry) для отслеживания заказов.
- Настройка алертинга на критичные события.

**Ресурсы:** DevOps-инженер + один бэкенд-разработчик, 4–6 недель.

### 2. I2 — Обеспечение надёжности обмена сообщениями через RabbitMQ

**Почему:** Потеря заказов — причина №1 оттока B2B-клиентов и недовольства B2C. Это непосредственная причина потери крупных контрактов. Производственные мощности позволяют справиться с нагрузкой — значит, проблема не в производстве, а в доставке заказов до производства.

**Состав работ:**
- Аудит текущей конфигурации RabbitMQ: durable-очереди, persistent-сообщения, ack-подтверждения.
- Внедрение Dead Letter Queue (DLQ) для обработки необработанных сообщений.
- Реализация механизма retry с exponential backoff.
- Обеспечение идемпотентности обработчиков сообщений (защита от дублей).
- Мониторинг очередей (длина, rate, ошибки).
- Кластеризация RabbitMQ (включая I7 как часть этой инициативы).

**Ресурсы:** один бэкенд Java-разработчик + один C#-разработчик + DevOps, 3–4 недели.

### 3. I3 — Внедрение API Gateway с rate-limiting

**Почему:** После открытия API компанию «завалило» заказами, и MES API не справляется. Внешний трафик не контролируется и напрямую влияет на работу операторов. Это относительно быстрое изменение с высоким эффектом — защита внутренней системы от неконтролируемого внешнего давления.

**Состав работ:**
- Развёртывание API Gateway (Kong, Nginx или Yandex API Gateway).
- Настройка rate-limiting и квот для B2B-клиентов.
- Маршрутизация внешнего трафика через Gateway, внутренний трафик — напрямую.
- Аутентификация API-ключами для B2B.
- Мониторинг API-трафика через Gateway.

**Ресурсы:** DevOps-инженер + один бэкенд-разработчик, 2–3 недели.

## 6. Целевая архитектура решения

Целевая архитектура через полгода должна обеспечить **надёжность**, **наблюдаемость** и **контролируемый рост** при сохранении текущего технологического стека и размера команды.

### Ключевые изменения относительно текущего состояния

**Слой наблюдаемости (новый):**
- Централизованная система сбора метрик (Prometheus + Grafana) со всех компонентов.
- Централизованное логирование (OpenSearch / ELK) для Shop API, CRM API, MES API.
- Распределённый трейсинг (OpenTelemetry + Jaeger) — полный путь заказа от создания до закрытия.
- Алертинг при деградации SLO (время обработки заказа, потерянные сообщения, ошибки API).

**Слой интеграции (обновлённый):**
- RabbitMQ в кластерной конфигурации (3 ноды) с durable-очередями, persistent-сообщениями, DLQ и retry-механизмами.
- Идемпотентная обработка сообщений на стороне CRM API и MES API.
- API Gateway перед MES API для B2B-трафика с rate-limiting, аутентификацией и квотированием.

**Слой данных (обновлённый):**
- Shop DB — read-реплика для тяжёлых запросов на чтение (списки заказов, отчёты).
- MES DB — read-реплика для дашборда операторов.
- Redis-кеш перед MES DB для страницы дашборда (список заказов по статусам).
- Начата работа по разделению Shop DB (CRM получает свою БД, синхронизация через события).

**Слой приложений (обновлённый):**
- Shop API: 2 инстанса за балансировщиком нагрузки.
- MES API: 2 инстанса за балансировщиком нагрузки (разделение внутреннего и внешнего трафика).
- CRM API: 1 инстанс (нагрузка пока не требует масштабирования, но архитектура позволяет добавить).

**Процесс разработки:**
- CI/CD дополнен автоматическими E2E-тестами для критичных сценариев (создание заказа, смена статуса, расчёт стоимости).
- Среднее время релизного цикла сокращено за счёт автоматизации тестирования.
